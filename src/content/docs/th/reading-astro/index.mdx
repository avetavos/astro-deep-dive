## 1. Rendering mode & adapter

ก่อนอื่นให้หาก่อนว่าโค้ด Astro ชิ้นนี้ *รันตอนไหน* — ตอน build ครั้งเดียว หรือทุกครั้งที่มี request บน server — เพราะทุกคำถามถัดไป (อ่าน cookie ได้ไหม ต้องมี adapter หรือเปล่า header จะทำงานจริงไหม) ขึ้นกับคำตอบนี้ทั้งหมด โค้ดที่ AI เขียนมักสมมติว่าหน้าเพจ render ต่อ request ทั้งที่จริง ๆ ถูก prerender ไว้ (หรือตรงข้ามกัน) และ training data ที่เก่ากว่า Astro v5 ยังใช้ระบบสามโหมดที่ Astro ไม่มีแล้ว

- **สิ่งที่ต้องมองหา:** โปรเจกต์ (หรือ route นั้น ๆ) ตั้ง `export const prerender = false` ไว้จริงหรือไม่ หรือพึ่ง `output: 'server'` ระดับโปรเจกต์อยู่? config ยังตั้ง `output: 'hybrid'` — ค่าที่ Astro v5 เอาออกไปแล้ว — อยู่หรือเปล่า? มี adapter ตั้งค่าไว้หรือไม่ ถ้ามี route ใด (หรือ Action หรือ server island) ต้องการ on-demand rendering? มีหน้าที่อ่าน `Astro.cookies`, `Astro.session`, หรือ `Astro.request.headers` ทั้งที่รอบข้างยังบอกว่าเป็น static อยู่หรือไม่?
- **คำถามที่ต้องถาม:** HTML ของไฟล์นี้ขึ้นกับว่าใครเป็นคนถามจริง ๆ หรือเหมือนกันทุกคน — และการประกาศ rendering mode ของโค้ดเองตรงกับคำตอบนั้นจริงหรือไม่?
- **บทเรียนที่อธิบายเรื่องนี้:** **[Rendering & Output Modes](/astro/th/foundations/rendering-and-output-modes/)** สำหรับ static กับ on-demand และ build warning จริงที่พิสูจน์แล้วเมื่อหน้า prerender อ่าน request data; **[SSR & Adapters](/astro/th/server-side/ssr-and-adapters/)** สำหรับ adapter, `output`, และเหตุผลที่ `'hybrid'` เป็นคำเก่าไปแล้ว

## 2. Island & client directive

พอรู้แล้วว่าอะไร render ตอนไหน ต่อไปดูว่าอะไรถูกส่งไปที่ browser จริง ๆ component จาก framework ที่ import เข้า `.astro` จะเป็น static HTML จนกว่าจะมี client directive แปลงมันเป็น island — และ directive ที่ LLM มักเลือกโดยปริยายแทบไม่ใช่ตัวที่ถูกต้องเลย

- **สิ่งที่ต้องมองหา:** component ที่โต้ตอบได้ทุกตัวเป็น `client:load` ไม่ว่าจะอยู่ตำแหน่งไหนของหน้าหรือไม่? `client:only` เคยปรากฏโดยไม่ระบุ framework บ้างไหม? prop ที่ส่งเข้า island เป็นค่าธรรมดา (serializable) หรือเป็น function/class instance ที่ wire format ส่งข้ามไปไม่ได้? component จาก framework (`.tsx`/`.jsx`) ใช้ `<slot />` แบบของ Astro เอง โดยคาดหวังว่ามันจะทำงานเหมือนตอนอยู่ใน `.astro` หรือไม่?
- **คำถามที่ต้องถาม:** component นี้ต้องโต้ตอบได้ทันทีที่หน้าโหลดจริงหรือ หรือ trigger ที่ช้ากว่า (`client:visible`, `client:idle`) ก็เพียงพอโดยใช้ JavaScript ต้นทางน้อยกว่า — และ prop ทุกตัวที่ island นี้รับจะรอดจากการถูก serialize ลง HTML จริงหรือไม่?
- **บทเรียนที่อธิบายเรื่องนี้:** **[Client Directives](/astro/th/islands/client-directives/)** สำหรับ directive ทั้งห้า, markup จริงของ `<astro-island>`, และ error `NoClientOnlyHint` ที่พิสูจน์แล้ว; **[Framework Integrations](/astro/th/islands/framework-integrations/)** สำหรับสิ่งที่เปลี่ยนไปเมื่อมี UI framework มากกว่าหนึ่งตัว; **[Sharing State](/astro/th/islands/sharing-state/)** สำหรับ state ที่ต้องข้าม island boundary อย่างถูกต้อง

## 3. Content & data

Content collection คือจุดที่ training data ก่อน v5 เก่าที่สุดเห็นได้ชัด — API ทั้งหมด (ต้องมี `loader`, `render(entry)` เป็น standalone function, `Astro.glob()` หายไป) เปลี่ยนรูปร่าง และโค้ดที่หน้าตาเก่าจะพังในแบบที่ระบุชื่อได้ ไม่ใช่แค่ "compile ไม่ผ่าน"

- **สิ่งที่ต้องมองหา:** ทุกการเรียก `defineCollection` ประกาศ `loader` หรือไม่? โค้ดเรียก `entry.render()` แบบ method แทนที่จะ import `render` จาก `astro:content` หรือเปล่า? dynamic route ที่ควรเป็น static export `getStaticPaths()` จริงหรือไม่? frontmatter ถูกตรวจสอบด้วย schema ที่ตรงกับ field จริงหรือไม่? มีที่ไหนยังเรียก `Astro.glob()` อยู่หรือไม่?
- **คำถามที่ต้องถาม:** นี่คือ Content Layer API ปัจจุบัน (มี `loader`, Zod `schema`, `render(entry)`) หรืออ่านแล้วเหมือน tutorial ที่เขียนก่อน Astro 5 — และ `astro check`/`astro sync` จะจับความต่างนี้ได้จริงไหม หรือต้อง build จริงเท่านั้นถึงจะเห็น?
- **บทเรียนที่อธิบายเรื่องนี้:** **[Content Collections](/astro/th/content-and-data/content-collections/)** สำหรับรูปร่าง `loader`/`schema` และ runtime error จริงของ `entry.render()`; **[Dynamic Routes](/astro/th/content-and-data/dynamic-routes/)** สำหรับ `getStaticPaths()` และ build error ที่มีชื่อจริงของมัน; **[Data Fetching](/astro/th/content-and-data/data-fetching/)** สำหรับเหตุผลที่ `Astro.glob()` กลายเป็น type error ไม่ใช่แค่สไตล์การเขียน; **[Schemas & References](/astro/th/content-and-data/schemas-and-references/)** สำหรับ error การตรวจสอบ Zod จริงเมื่อ schema กับ frontmatter ไม่ตรงกัน

## 4. Astro ฝั่ง server

พื้นผิวฝั่ง server ของ Astro — Action, endpoint, middleware, session — หน้าตาเหมือนการเรียกฟังก์ชันธรรมดาจากในโค้ดเบส ซึ่งนั่นแหละที่ทำให้ลืมง่ายว่าส่วนใหญ่มันก็เป็น endpoint สาธารณะด้วย ทันทีที่เป็น on-demand

- **สิ่งที่ต้องมองหา:** handler ของ Action ตรวจ `context.locals.user` (หรือเทียบเท่า) เป็นบรรทัดแรกหรือไม่ หรือสมมติว่าผู้เรียกถูก authenticate แล้วเพราะ *form* render เฉพาะหลัง login? middleware เรียก (และ return) `next()` ในทุกเส้นทางของฟังก์ชันเสมอหรือไม่? หลัง login แล้ว มีการ regenerate session บ้างไหม?
- **คำถามที่ต้องถาม:** ถ้า `curl` endpoint นี้ตรง ๆ โดยไม่มี session cookie เลย จะเกิดอะไรขึ้น — และคำตอบนั้นตรงกับสิ่งที่ UI เองกันไว้หรือไม่?
- **บทเรียนที่อธิบายเรื่องนี้:** **[Actions](/astro/th/server-side/actions/)** สำหรับ 401 จริงที่พิสูจน์แล้วเมื่อไม่มีการตรวจ auth; **[Middleware & Sessions](/astro/th/server-side/middleware-and-sessions/)** สำหรับลำดับของ `sequence()`, `context.locals`, และ session fixation; **[Endpoints & API Routes](/astro/th/server-side/endpoints-and-api-routes/)** สำหรับกฎการเข้าถึงสาธารณะแบบเดียวกันที่ใช้กับ endpoint ธรรมดา

## 5. Security

จุดพังด้าน security เฉพาะของ Astro ที่พบซ้ำ ๆ ในโค้ดที่ AI เขียนมีสองแบบ และไม่มีแบบไหนเป็น compiler error เลย: การฉีด HTML ดิบ กับ secret ที่หลุดจากโค้ดฝั่ง server ไปยังสิ่งที่ browser ได้รับจริง

- **สิ่งที่ต้องมองหา:** `set:html` เคย render string ที่ย้อนกลับไปหา input ของ user โดยไม่มี sanitizer จริงคั่นกลางหรือไม่? ค่าที่อ่านจาก `import.meta.env`/`astro:env/server` เคยถูกส่งเป็น prop ให้ island ที่ client hydrate หรือไม่ — แม้ module ต้นทางจะเป็น server-only จริง ๆ ก็ตาม?
- **คำถามที่ต้องถาม:** ถ้าค่านี้ไปโผล่ใน source ของหน้า (view-source ไม่ใช่แค่ log ฝั่ง server) ยอมรับได้ไหม — และมีอะไรใน code path นี้ที่หยุดสิ่งนั้นจริง ๆ หรือแค่ดูเหมือนหยุดเฉย ๆ?
- **บทเรียนที่อธิบายเรื่องนี้:** **[Astro Syntax Deep Dive](/astro/th/components/astro-syntax-deep/)** สำหรับ payload XSS จริงที่ `set:html` รันออกมา พิสูจน์ด้วย Container API; **[SSR & Adapters](/astro/th/server-side/ssr-and-adapters/)** สำหรับสิ่งที่ boundary `context`/`access` ของ `astro:env` บังคับใช้จริง — และสำคัญพอ ๆ กัน สิ่งที่มันไม่ได้บังคับ

## 6. Performance & cache

Astro มีคันโยกหลายอันที่ *ฟังดู* เหมือนเป็นอันเดียวกัน — cache header, config route cache, การ optimize รูป, script ที่ใช้ร่วมกันกับที่ซ้ำ, DOM ที่ persist ข้ามการนำทาง — และโค้ดที่ AI เขียนมักสมมติว่าคันโยกหนึ่งทำหน้าที่ของอีกอันหนึ่ง

- **สิ่งที่ต้องมองหา:** `routeRules`/`cache` ถูกมองว่าเป็นตัวตั้ง header `Cache-Control` ที่ browser เห็นหรือไม่? `is:inline` ถูกใช้กับ script ที่ตั้งใจให้รันครั้งเดียว ใช้ร่วมกันต่อหน้าหรือไม่? `<Image>` ระยะไกลที่ hardcode `width`/`height` สมมติว่า `image.domains` ป้องกันมันอยู่หรือไม่? `transition:persist` ปรากฏบน element ที่ไม่มีคู่ตรงกันแน่นอนบนหน้าปลายทางหรือไม่?
- **คำถามที่ต้องถาม:** ตาม header, script tag, หรือ node ที่ persist นี้ไปจนถึงสิ่งที่ browser จริงได้รับ — มันเป็นกลไกที่โค้ดสมมติไว้จริงหรือเป็นอีกกลไกหนึ่งที่ชื่อคล้ายกัน?
- **บทเรียนที่อธิบายเรื่องนี้:** **[Caching & Edge](/astro/th/rendering-and-performance/caching-and-edge/)** สำหรับความต่างจริงที่พิสูจน์แล้วระหว่าง `Astro.response.headers` กับ `routeRules`/`cache`; **[Images & Assets](/astro/th/rendering-and-performance/images-and-assets/)** สำหรับจุดที่ `image.domains` บังคับใช้จริง (และไม่บังคับใช้); **[View Transitions](/astro/th/rendering-and-performance/view-transitions/)** สำหรับการจับคู่ของ `transition:persist` และ `<ClientRouter />` ที่เปลี่ยนชื่อ

## 7. Tooling & production

สุดท้าย ตรวจว่าการตั้งค่าโปรเจกต์รอบข้าง — config key, คำสั่งที่ใช้ "ทดสอบ" build production — เป็นปัจจุบันหรือไม่ เพราะโค้ดที่ AI เขียนอาจถูกต้องเฉพาะจุด แต่ยังอยู่ใน setup ที่เก่าหรือทำให้เข้าใจผิด

- **สิ่งที่ต้องมองหา:** `astro.config.mjs` ยังตั้ง `markdown.remarkPlugins`/`rehypePlugins`/`gfm` เป็น top-level key ของ `markdown.*` อยู่หรือไม่? `astro preview` เคยถูกใช้ (หรือ script ให้รัน) เป็น production server จริงหรือไม่?
- **คำถามที่ต้องถาม:** schema config ของ Astro เวอร์ชันที่ *ติดตั้งจริง* ยังรับ key นี้ตามที่โค้ดสมมติไว้หรือไม่ — และคำสั่งที่ใช้ "พิสูจน์ว่าใช้งานได้จริงบน production" เป็นคำสั่งที่เอกสารของ Astro เองบอกว่าใช้แบบนั้นได้อย่างปลอดภัยจริงหรือไม่?
- **บทเรียนที่อธิบายเรื่องนี้:** **[Config & Integrations](/astro/th/tooling-and-production/config-and-integrations/)** สำหรับ Markdown key ระดับบนสุดที่เลิกใช้แล้ว; **[Testing & Tooling](/astro/th/tooling-and-production/testing-and-tooling/)** สำหรับ exit code ของ `astro check` และตำแหน่งของ `eslint-plugin-astro`

## ความเข้าใจผิดที่พบบ่อย

- **"ถ้า `astro check` ผ่าน แปลว่าโค้ดถูกต้อง"** entry ส่วนใหญ่ใน catalog ของโมดูลนี้ผ่าน `astro check` สะอาด — มันแค่ type-check `.astro`/`.ts`/`.tsx` ไม่ได้รันหน้าเพจ ไม่ได้ build จริง ไม่ได้ยิง request ไปที่ endpoint
- **"โค้ด Astro ที่ AI เขียนแค่ต้องการ prompt ใหม่กว่านี้"** ปัญหาไม่ใช่แค่ความเก่า — `output: 'hybrid'`, `Astro.glob()`, และ `<ViewTransitions />` คือ Astro ที่ *ดูลื่นไหลน่าเชื่อถือ* syntax ถูกต้องทุกอย่าง แต่บังเอิญเล็งไปที่เวอร์ชันที่ 7.3.5 ที่ติดตั้งในคอร์สนี้ไม่มีแล้ว
- **"ความล้มเหลวแบบเงียบเกิดน้อยกว่า build error เลยสำคัญน้อยกว่า"** ใน catalog นี้ตรงข้ามเลย: secret ที่หลุดใน prop ที่ serialize ของ island หรือ `transition:persist` ที่หยุด persist แบบเงียบ ๆ ขึ้น production ได้โดยไม่มี error ไม่มี warning ไม่มีสัญญาณอะไรเลยว่ามีอะไรผิด
- **"โมเดล rendering ของ Astro เรียบง่าย เลยมีอะไรให้ review น้อยกว่า framework ฝั่ง client"** Astro เพิ่มแกนที่ framework ฝั่ง client ไม่มีเลย — *เวลาที่* โค้ดชิ้นหนึ่งรัน (ตอน build หรือตอน request) เปลี่ยนสิ่งที่ API ทุกตัวใน catalog นี้ได้รับอนุญาตให้ทำ
