## ปัญหาเรื่องการแยกตัว

island hydrate อย่างเป็นอิสระ — นั่นแหละที่ทำให้ต้นทุนถูก แต่มีผลข้างเคียงที่คนมาจาก SPA มักสะดุด: **island สองตัวไม่แชร์ state กันอัตโนมัติ** `useState` ของ React ใน island หนึ่งมองไม่เห็นจากอีก island หนึ่ง แม้จะสร้างจาก framework เดียวกันก็ตาม ไม่มี app tree ร่วมกัน แต่ละ island เป็น root เล็ก ๆ ของตัวเอง

## พิสูจน์: Preact context เดียวกัน สอง island ก็ยังไม่แชร์กัน

"ไม่มี app tree ร่วมกัน" ไม่ได้จริงแค่กับ `useState` — จริงกับ **`createContext`** ด้วย และนี่คือความเข้าใจผิดที่ควรพิสูจน์ตรง ๆ เพราะ `Provider` *ดูเหมือน* ควรจะไปถึงทุกที่ แต่มันไปไม่ถึงข้าม boundary ของ island เลย:

```ts
// src/context.ts
import { createContext } from 'preact';

export const CountContext = createContext(0);
```

```tsx
// src/components/ProviderIsland.tsx
import { CountContext } from '../context.ts';
import ReaderIsland from './ReaderIsland';

export default function ProviderIsland() {
  return (
    <CountContext.Provider value={42}>
      <p>ProviderIsland's own child sees: <ReaderIsland label="inside-provider-island" /></p>
    </CountContext.Provider>
  );
}
```

```tsx
// src/components/ReaderIsland.tsx
import { useContext } from 'preact/hooks';
import { CountContext } from '../context.ts';

export default function ReaderIsland({ label }: { label: string }) {
  const value = useContext(CountContext);
  return <span data-testid={label}>{label}: {String(value)}</span>;
}
```

```astro
---
// src/pages/context-demo.astro
import ProviderIsland from '../components/ProviderIsland.tsx';
import ReaderIsland from '../components/ReaderIsland.tsx';
---
<div id="a"><ProviderIsland client:load /></div>
<div id="b"><ReaderIsland label="separate-island" client:load /></div>
```

build แล้ว render จริง `ReaderIsland` สองตัวเห็นค่า**ต่างกัน** ทั้งที่อ่าน `CountContext` ตัวเดียวกันเป๊ะ:

```html
<span data-testid="inside-provider-island">inside-provider-island: 42</span>
<span data-testid="separate-island">separate-island: 0</span>
```

`ReaderIsland` ตัวแรกเป็น child ของ `ProviderIsland` เอง — render tree เดียวกัน `Provider` เดียวกัน เลยเห็น `42` ส่วน `ReaderIsland` ตัวที่สองเป็น **island แยกต่างหาก** ระดับบนสุดในหน้าเดียวกัน มันไม่เคยเข้าไปใน tree ของ `ProviderIsland` เลย ทำให้ `useContext(CountContext)` ตกกลับไปที่ default ของ context เอง (`0`) — ไม่ error แค่เงียบ ๆ ผิดค่า เป็นแบบนี้ตั้งแต่ตอน render บน server ก่อนที่ client JS ตัวไหนจะรันด้วยซ้ำ เพราะ `<... client:... />` แต่ละตัวในไฟล์ `.astro` ได้ render call ของตัวเองแยกกัน

แล้ว island "add to cart" กับ island "cart count" ที่ header จะ sync กันได้ยังไง ในเมื่อทั้ง `useState` และ `Context` ไม่ข้าม boundary ของ island เลย? คุณมีเครื่องมือสามอย่าง เรียงจากง่ายที่สุดไปทรงพลังที่สุด

## 1. ส่ง serializable props จาก server

ถ้าข้อมูลรู้อยู่แล้วตอนหน้า render คำตอบที่ง่ายที่สุดคือคำนวณครั้งเดียวในไฟล์ `.astro` แล้วส่งให้แต่ละ island เป็น **prop** ไม่ต้องประสานงานข้าม island เลย — server คือแหล่งข้อมูลร่วม

```astro
---
import CartBadge from '../components/CartBadge.jsx';
const initialCount = await getCartCount(Astro.request);
---
<CartBadge count={initialCount} client:load />
```

อันนี้ครอบคลุม state *เริ่มต้น* แต่ไม่ช่วยตอนที่ island หนึ่งต้อง *อัปเดต* อีกตัวตอน runtime — นั่นคือสิ่งที่ store มีไว้

## 2. nanostores สำหรับ state ที่แชร์ข้าม island

เมื่อ island ต้องตอบสนองต่อกันตอน runtime ให้ใช้ **shared store** ที่อยู่นอก island ตัวใดตัวหนึ่ง เอกสารของ Astro แนะนำ **nanostores** — ขนาดเล็กมาก ไม่ผูกกับ framework ใด และมี adapter สำหรับแต่ละ framework (`@nanostores/react`, `@nanostores/vue`, ...) คุณนิยาม store ครั้งเดียว แล้ว island ไหนก็อ่านและเขียน store นี้ได้

```js
// src/stores/cart.js
import { atom } from 'nanostores';
export const cartCount = atom(0);
```

```jsx
// AddToCart.jsx (React island)
import { cartCount } from '../stores/cart.js';
export default function AddToCart() {
  return <button onClick={() => cartCount.set(cartCount.get() + 1)}>Add</button>;
}
```

```jsx
// CartBadge.jsx (another React island, elsewhere on the page)
import { useStore } from '@nanostores/react';
import { cartCount } from '../stores/cart.js';
export default function CartBadge() {
  const count = useStore(cartCount);   // re-renders when the store changes
  return <span>Cart: {count}</span>;
}
```

ตอนนี้กดปุ่ม "Add" ใน island หนึ่งจะอัปเดต badge ใน island ที่แยกกันคนละที่ — เพราะทั้งคู่ subscribe store เดียวกัน ไม่ได้ subscribe กันเอง

### พิสูจน์ end-to-end ด้วย `@nanostores/preact`

รูปแบบข้างบนเป็นเรื่องจริง เช็คด้วย framework ของคอร์สนี้เอง (`useStore` ของ `@nanostores/preact`) และ browser session จริง ไม่ใช่แค่อธิบายเฉย ๆ:

```ts
// src/stores/cart.ts
import { atom } from 'nanostores';

export const cartCount = atom(0);
```

```tsx
// src/components/AddToCart.tsx
import { cartCount } from '../stores/cart.ts';

export default function AddToCart() {
  return (
    <button data-testid="add-btn" onClick={() => cartCount.set(cartCount.get() + 1)}>
      Add
    </button>
  );
}
```

```tsx
// src/components/CartBadge.tsx
import { useStore } from '@nanostores/preact';
import { cartCount } from '../stores/cart.ts';

export default function CartBadge() {
  const count = useStore(cartCount);
  return <span data-testid="cart-badge">Cart: {count}</span>;
}
```

ทั้งคู่ mount เป็น **island แยกกัน ระดับบนสุด** บนหน้าเดียว (`<CartBadge client:load />` ที่ header, `<AddToCart client:load />` ที่ body — ไม่มีความสัมพันธ์ parent/child เลย) ขับด้วย browser จริง:

```text
document.querySelector('[data-testid=cart-badge]').textContent   // "Cart: 0"
// ...click [data-testid=add-btn] twice...
document.querySelector('[data-testid=cart-badge]').textContent   // "Cart: 2"
```

สองคลิกที่ปุ่มของ `AddToCart` อัปเดต `CartBadge` ใน island tree ที่แยกกันคนละอัน — นี่คือสิ่งเดียวที่ `useState`/`Context` ทำไม่ได้ (พิสูจน์ข้างบน) แต่ nanostore ทำได้ เพราะทั้งสอง island subscribe object store ตัวเดียวกัน ไม่ได้ subscribe component tree ของกันเอง

## 3. slot: ส่ง children ที่ render บน server เข้าไปใน island

บางครั้งคุณไม่ได้ต้องแชร์ *state* — แต่ต้องเอา **content ที่ render บน server** ไปวางในเปลือกที่ interactive framework island รับ `<slot />` ได้แบบเดียวกับ `.astro` component ดังนั้น island `<Tabs>` ที่ interactive จึงห่อ panel ที่ static และ render บน server ไว้ได้ เปลือกเป็น interactive ส่วน content ถูกส่งเป็น HTML โดยไม่มี island JS เพิ่ม

```astro
---
import Accordion from '../components/Accordion.jsx';
---
<Accordion client:visible>
  <p>This paragraph is server-rendered HTML, passed into the island via its slot.</p>
</Accordion>
```

## รอดจาก navigation: `transition:persist`

props กับ store ตอบคำถาม "island บน**หน้าเดียวกัน**แชร์ state กันยังไง" `transition:persist` ตอบคำถามคนละแบบ: **state ภายในของ island เดียว** จะรอดจากการ navigate แบบ client-side ด้วย `ClientRouter` ของ Astro ได้ยังไง ในเมื่อหน้าถัดไป render component "ตัวใหม่" ของ component เดียวกัน?

ห่อ island ด้วย element ที่มี `transition:persist` (ชื่อคงที่ ให้ Astro จับคู่ข้ามสองหน้าได้) บน**ทั้งสอง**หน้า:

```tsx
// src/components/PersistCounter.tsx
import { useState } from 'preact/hooks';

export default function PersistCounter({ start }: { start: number }) {
  const [count, setCount] = useState(start);
  return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}
```

```astro
---
// src/pages/persist-a.astro
import { ClientRouter } from 'astro:transitions';
import PersistCounter from '../components/PersistCounter.tsx';
---
<html>
<head><ClientRouter /></head>
<body>
<h1>Page A</h1>
<div transition:persist="shared-counter">
  <PersistCounter start={0} client:load />
</div>
<a href="/persist-b/">Go to B</a>
</body>
</html>
```

```astro
---
// src/pages/persist-b.astro
import { ClientRouter } from 'astro:transitions';
import PersistCounter from '../components/PersistCounter.tsx';
---
<html>
<head><ClientRouter /></head>
<body>
<h1>Page B</h1>
<div transition:persist="shared-counter">
  <PersistCounter start={0} client:load />
</div>
<a href="/persist-a/">Back to A</a>
</body>
</html>
```

ทั้งสองหน้า mount `PersistCounter` ด้วย `start={0}` — ถ้า DOM ถูกทิ้งแล้วสร้างใหม่ count ต้องรีเซ็ตเป็น `0` พิสูจน์ด้วย browser session จริงแทน: บนหน้า A คลิกจริงสามครั้งทำให้ปุ่มขึ้น `Count: 3` แล้วคลิก link จริง `<a href="/persist-b/">` (navigate แบบ client-side ที่ `ClientRouter` ดักไว้ ไม่ใช่ reload เต็มหน้า):

```text
// Page A, after 3 clicks:
document.querySelector('button').textContent   // "Count: 3"

// after clicking the real <a href="/persist-b/"> link:
document.querySelector('h1').textContent       // "Page B"
document.querySelector('button').textContent   // "Count: 3"  — NOT reset to "Count: 0"
```

DOM node (พร้อม component instance ที่มีชีวิตอยู่ พร้อม `useState` ของตัวเอง) ถูกย้ายข้ามการสลับหน้า ไม่ได้ถูกทำลายแล้วสร้างใหม่ — `start={0}` บน markup ของหน้า B ไม่ได้ถูกใช้เลยด้วยซ้ำ ทำงานแบบนี้ได้ก็เพราะทั้งสองฝั่งใช้ค่า `transition:persist` **เดียวกัน** — พิมพ์ผิดไม่ตรงกันจะเสียการ persist แบบเงียบ ๆ แล้ว mount ใหม่เฉย ๆ

## เลือกจากสามอย่าง

- ข้อมูลรู้ตอน render ไม่มีอัปเดต runtime → **props จาก server**
- island ต้องอัปเดตกันตอน runtime → **nanostore**
- ต้องการ chrome ที่ interactive ครอบ content ที่ static → **slot**

คว้า store มาใช้เฉพาะตอนที่มีการประสานงาน runtime ระหว่าง island แยก ๆ จริง ๆ ความต้องการ "shared state" ส่วนใหญ่กลายเป็น props เริ่มต้นหรือ slot ซึ่งส่ง JavaScript น้อยกว่า

### props เทียบ store: คำนวณใหม่ กับ แบบ live

prop กับ store ดูเหมือนแก้ปัญหาเดียวกัน แต่ตอบคำถามคนละแบบเรื่อง *เมื่อไหร่* ที่ค่าถูกตัดสิน:

- **prop** ถูกตัดสินครั้งเดียว บน server ตอนที่ request นั้น ๆ render island สองตัวที่ได้ prop เดียวกันตรงกันแค่ ณ ตอน render นั้น — refresh หรือไม่ refresh คือคันโยกเดียวที่มี ไม่มีเส้นทาง "prop เปลี่ยนแล้ว re-render ที" หลัง hydrate ถ้าค่าที่ server คำนวณไว้ล้าสมัย ทางแก้มีแค่ navigate ใหม่หรือ `fetch` เองข้างใน island
- **store** เป็นค่าฝั่ง client ที่ live อยู่ได้เองไม่ขึ้นกับ render ไหน ทุก island ที่ subscribe re-render ทันทีที่ `.set()` ถูกเรียก ไม่มี round-trip ไป server เลย — พิสูจน์ข้างบนแล้วว่าไม่มีการ reload หน้าเลยระหว่างสองคลิกกับการอัปเดต badge

### เมื่อไหร่ store คือของเกินความจำเป็น

ถ้าคุณกำลังจะคว้า nanostore มาใช้ แต่สอง island ไม่ได้ต้องตอบสนองต่อ*กันเอง*จริง ๆ — แค่ต้องการข้อมูลของตัวเองแยกกัน — store แค่เพิ่มชั้นอ้อมเหนือสิ่งที่ prop แต่ละตัวทำได้ง่ายกว่า สัญญาณที่ชัดเจน: ถ้าคำนวณค่าเริ่มต้นของทั้งสอง island ได้จาก request เดียวกัน และไม่มีตัวไหนต้องเปลี่ยนเพราะสิ่งที่*อีกตัว*ทำ นั่นไม่ใช่ cross-island state เลย มันคือ island สองตัวที่ต่างก็อยากได้ prop ของตัวเอง

## อ่านโค้ดที่ AI เขียน

ตอนเจอ snippet ที่ generate มาประสาน state ข้าม island เช็คสิ่งเหล่านี้ก่อนเชื่อ:

- มันห่อ island หลายตัวด้วย `Context.Provider` ตัวเดียวแล้วคาดหวังให้ทุกตัวอ่านได้ไหม? พิสูจน์ข้างบน: `Provider` ไปถึงแค่ render tree ของ island **ตัวเอง** — island พี่น้องที่อ่าน context เดียวกันจะได้ default ของ context ไม่ใช่ค่าที่ provide ไว้ โดยไม่มี error เตือนเลย
- ตัวอย่างสไตล์ "add to cart" ใช้ `useState` ที่ยกขึ้นไปเป็น "parent" แล้วคาดหวังให้ parent กับ child island แชร์กันได้เองไหม? ถ้าเป็น `client:*` island แยกกัน (ไม่ใช่ component tree เดียวที่มีความสัมพันธ์ parent/child ของ JSX จริงอยู่ใน island เดียว) การยก state ขึ้นไปใช้ไม่ได้ ให้ใช้ store แทน
- ถ้ามีการเอา nanostore มาใช้ มันจำเป็นจริงไหม — สอง island ต้องอัปเดตซึ่งกันและกันจริง ๆ หรือแค่ต่างฝ่ายต่างรับ prop ที่ server คำนวณมาให้ก็พอ?
- `transition:persist` ปรากฏโดยไม่มีค่า**เดียวกัน**ทั้งสองฝั่งของการ navigate ไหม? ชื่อไม่ตรงกันจะทำให้ persist ล้มเหลวแบบเงียบ ๆ — component แค่ mount ใหม่เฉย ๆ ซึ่งดูเหมือน bug ใน component มากกว่าจะดูเหมือนพิมพ์ผิดใน directive
- content ที่ render บน server ผ่าน slot ถูก re-implement เป็น prop ธรรมดา (HTML แบบ string หรือแย่กว่านั้นคือ fetch ใหม่ข้างใน island) ทั้งที่สิ่งที่ต้องการจริง ๆ แค่ "เอา content static นี้ไปไว้ในเปลือกที่ interactive" ไหม?

ทั้งสอง component ถูก mount เป็น island ระดับบนสุดของตัวเอง (แต่ละตัวได้ `client:*` directive ของตัวเองในไฟล์ `.astro`) — พิสูจน์ไปแล้วก่อนหน้านี้ในบทนี้ด้วยรูปแบบเดียวกัน (`ProviderIsland`/`ReaderIsland`): `UserContext.Provider` ของ `Sidebar` ห่อแค่ render tree ของ `Sidebar` เอง ไม่ห่อของ `Greeting` `Greeting` เป็น island แยกต่างหากที่มี `useContext(UserContext)` ของตัวเอง ซึ่งตกกลับไปที่ default ที่ `createContext(...)` ให้ไว้ — พิสูจน์ข้างบนแล้วว่าเป็นรูปแบบ `0`/`undefined` ไม่ใช่ `user` จริง ไม่มี error เลย มีแค่ "Guest" ที่ผิดตลอดไป ทางแก้คือหนึ่งในสามเครื่องมือ: ส่ง `user` เป็น **prop** ให้ `Greeting` ตรง ๆ จากไฟล์ `.astro` (ง่ายที่สุด ถ้ารู้ตอน render) หรือใส่ **nanostore** ถ้าต้องอัปเดตหลัง login โดยไม่ reload เต็มหน้า
</SpotTheBug>

## Mental Model

`client:*` directive แต่ละตัวบนหน้าคือ root ของ**แอปที่เป็นอิสระอย่างสมบูรณ์ของตัวเอง** — อิสระพอ ๆ กับเปิดสอง browser tab แยกกันแล้วคาดหวังให้แชร์ `useState` กันได้ ไม่มีอะไรที่ JSX ของ island เอง (`Provider`, `useState` ของ parent, ref) ไปถึงเกิน boundary ของ island ตัวเอง ช่องทางเดียวที่ข้าม boundary ได้คือช่องที่ Astro (props, `transition:persist`) หรือ library (store) ต่อสายให้เราโดยเฉพาะ

## ข้อแลกเปลี่ยน

| | props จาก server | nanostore | `<slot />` | `transition:persist` |
|---|---|---|---|---|

| **ต้องใช้ library ไหม** | ไม่ | ต้อง (nanostores + adapter ของ framework) | ไม่ | ไม่ — มีใน `ClientRouter` ของ Astro อยู่แล้ว |

| **อัปเดตข้าม island ตอน runtime ได้ไหม** | ไม่ | ได้ — พิสูจน์ข้างบน | N/A | N/A (island เดิม คนละหน้า) |

## ความเข้าใจผิดที่พบบ่อย

- **"ห่อ island ด้วย `Context.Provider` เดียวกันจะแชร์ state ระหว่างกันได้"** พิสูจน์ข้างบนแล้วด้วย `ProviderIsland`/`ReaderIsland`: `Provider` ไปถึงแค่ render tree ของ island ตัวเอง island พี่น้องเห็นแค่ default ของ context แบบเงียบ ๆ
- **"ถ้า island สองตัวต้องการข้อมูลเดียวกัน นั่นคืองานของ store โดยอัตโนมัติ"** พิสูจน์ข้างบนแล้ว: ถ้าข้อมูลไม่เปลี่ยนเพราะสิ่งที่อีก island ทำ prop ที่ server คำนวณมาให้ร่วมกันง่ายกว่าและส่ง JS น้อยกว่า store
- **"`transition:persist` re-fetch หรือคำนวณ component ใหม่บนหน้าใหม่"** พิสูจน์ข้างบนแล้วว่า DOM node กับ component instance เดิมย้ายข้ามการสลับหน้าไปเลย — prop ของ component นั้นบนหน้าใหม่ (`start={0}`) ไม่ถูกใช้เลยด้วยซ้ำ
- **"nanostore ต้องมี `Provider` เฉพาะ framework ห่อทั้งแอป เหมือน React Context"** nanostores ไม่มี provider เลย — พิสูจน์ข้างบนแล้วว่า `useStore(cartCount)` ทำงานได้เองจาก island ไหนก็ตามที่ import store module เดียวกัน เพราะ store อยู่ใน plain JS module ไม่ใช่ component tree

<Callout title="สรุปหนึ่งบรรทัด">
island **แยกตัวจากกัน** — พิสูจน์ข้างบนแล้วว่าแม้แต่ `createContext` ที่ใช้ร่วมกันก็ไม่ข้าม boundary ของ island เพราะแต่ละ island เป็น render root ของตัวเองพร้อม default ของตัวเอง มีเครื่องมือสามอย่าง เรียงตามระดับ: ส่ง **serializable props** จากไฟล์ `.astro` เมื่อข้อมูลรู้ตอน render (ตัดสินครั้งเดียวต่อ request); ใช้ **nanostore** (ไม่ผูก framework, `useStore` ของ `@nanostores/preact` พิสูจน์ end-to-end ข้างบน) เมื่อ island แยก ๆ ต้องอัปเดตกันแบบ live ตอน runtime โดยไม่มี round-trip ไป server; และใช้ **`<slot />`** วาง content ที่ render บน server เข้าไปใน island ที่ interactive เครื่องมือที่สี่ `transition:persist` เป็นคนละแกนไปเลย — มันเก็บ state ภายในของ island *ตัวเดียว*ให้รอดจากการ navigate ด้วย `ClientRouter` (พิสูจน์ข้างบนแล้วว่า click count จริงรอดจากการ nav หน้าต่อหน้าจริง) แทนที่จะเป็นการแชร์ state ระหว่าง island บนหน้าเดียวกัน default เป็น props และ slot คว้า store มาใช้เฉพาะการประสานงาน runtime จริง ๆ
</Callout>
