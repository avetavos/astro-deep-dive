## Performance ที่เริ่มต้นด้วย ไม่ใช่ผูกเพิ่มทีหลัง

framework ส่วนใหญ่บังคับให้เราไปแย่ง performance กลับคืนมา: build app เสร็จ มันช้า แล้วค่อย optimize Astro กลับด้านนั้น — เรา *เริ่ม* ที่ baseline เร็วอยู่แล้ว (static HTML, zero JavaScript) หน้าที่ของเราคือไม่ทำให้มันหลุดไป JavaScript ฝั่ง client ทุก kilobyte คือสิ่งที่เราเพิ่มเข้าไปเองโดยตั้งใจ คำถามที่ต้องถามตลอดคือ "อันนี้จำเป็นต้อง ship จริงไหม"

## เลือก client directive ที่ถูกที่สุด

lesson เรื่อง island พูดถึง *อะไร* ที่ client directive แต่ละตัวทำไปแล้ว ส่วนนี้คือมุมมองด้าน *performance* directive ที่เราเลือกเป็นตัวกำหนดว่า JavaScript รันเท่าไรและรันเมื่อไร:

| Directive | ship & รัน JS | ใช้เมื่อ |
|-----------|-----------------|----------|
| `client:load` | ทันทีตอนโหลดหน้า | interactivity สำคัญ above-the-fold (พบน้อย) |
| `client:idle` | ตอน browser ว่าง | interactive แต่ไม่ต้องทันที |
| `client:visible` | ตอน scroll เข้ามาในจอ | island ที่อยู่ below-the-fold (default ที่ดีที่สุด) |
| `client:media` | เฉพาะที่ breakpoint | widget เฉพาะ mobile หรือ desktop |

กฎง่าย ๆ: **เลือก `client:visible` (หรือ `client:idle`) ก่อน `client:load`** แต่ควรพูดให้ชัดว่ามันให้อะไรจริง ๆ — พิสูจน์ด้านล่างด้วย build output จริง: `client:load` กับ `client:visible` บน component เดียวกัน ship byte เท่ากันเป๊ะ ต่างกันแค่*เวลา*ที่ byte พวกนั้นทำงาน

## Build output จริง: zero island เทียบกับ island เดียว

สามหน้า `astro build` จริงครั้งเดียว ขนาดไฟล์จริงอ่านด้วย `ls -l` — ไม่ใช่จำมา:

```astro
<!-- page with zero islands -->
<html><body><h1>Zero islands</h1><p>Static only.</p></body></html>
```

```html
<!-- the ENTIRE built HTML for the zero-island page -->
<!DOCTYPE html><html><script type="module" src="/_astro/page.N3PupzSu.js"></script><body><h1>Zero islands</h1><p>Static only.</p></body></html>
```

```astro
<!-- page with one Preact island -->
<Counter client:load />
```

```html
<!-- built HTML: one custom element, its own tiny chunk, plus the shared framework runtime -->
<astro-island uid="Z11idW2" data-preact-island-id="1"
  component-url="/_astro/Counter.D0Rq_C0J.js" component-export="default"
  renderer-url="/_astro/client.CYoOuZrL.js" props="{}" ssr client="load"
  opts="{&quot;name&quot;:&quot;Counter&quot;,&quot;value&quot;:true}" await-children>
  <button>Count: 0</button>
</astro-island>
```

`ls -l` จริงของ chunk ใน `_astro/` ที่ build ออกมา (byte ตัดเหลือเฉพาะไฟล์ที่เกี่ยวข้อง):

```text
$ ls -l dist/client/_astro/ | grep -v woff
-rw-r--r--  1634 ClientRouter.astro_astro_type_script_index_0_lang.CnHlC045.js
-rw-r--r--   573 Counter.D0Rq_C0J.js
-rw-r--r-- 12358 client.CMnqbhkF.js          <- unused by this page (ClientRouter's own runtime chunk)
-rw-r--r--  2738 client.CYoOuZrL.js          <- Preact renderer glue, used by Counter
-rw-r--r--    24 client.ChiJXsfH.js
-rw-r--r--  2438 hooks.module.C-rKEPwH.js
-rw-r--r--    47 page.N3PupzSu.js
-rw-r--r-- 10470 preact.module.Bl7PEaKa.js
-rw-r--r--  2537 prefetch.D-YIxd5A.js
-rw-r--r--  7798 signals.module.r9f66GF9.js
```

ทุกหน้า — **รวมถึงหน้า zero-island ด้วย** — โหลด `page.N3PupzSu.js` (**47 byte**) นั่นไม่ใช่ overhead ของ framework — มันคือ **prefetch** bootstrap แบบ global ที่ถูกเติมเข้ามาเพราะ config ของเว็บนี้เปิด `prefetch: { prefetchAll: true }` ไว้ ถ้าปิด prefetch ไปเลย หน้า zero-island จะ ship JS เป็นศูนย์จริง ๆ หน้าที่มี Preact counter หนึ่งตัวแบบ `client:load` (หรือ `client:visible`) เพิ่ม: inline hydration-runtime bootstrap (ฝังตรงใน HTML เลย ไม่ใช่ไฟล์แยก), `Counter.D0Rq_C0J.js` (573B, ตัว component เอง), `client.CYoOuZrL.js` (2738B, glue ของ Preact สำหรับ Astro renderer) และ chunk runtime ของ Preact ที่แชร์กัน (`preact.module` 10470B + `hooks.module` 2438B + `signals.module` 7798B = 20706B) — chunk ที่แชร์สามตัวนี้ถูก cache ครั้งเดียวต่อเว็บ และใช้ซ้ำโดยทุก island ของ Preact ไม่ได้ duplicate ต่อ island

## `client:load` เทียบ `client:visible`: byte เท่ากัน แต่*เวลา*ต่างกัน

build `<Counter />` ตัวเดียวกันเป๊ะ ด้วย `client:load` บนหน้าหนึ่ง และ `client:visible` บนอีกหน้า ได้ reference chunk `component-url`/`renderer-url` **เหมือนกัน** — ต่างกันแค่ inline bootstrap script ตัวไหนที่รัน และรันเมื่อไร:

```js
// client:load — real inline bootstrap, runs the hydrator immediately
(()=>{var e=async t=>{await(await t())()};(self.Astro||(self.Astro={})).load=e;window.dispatchEvent(new Event("astro:load"));})();
```

```js
// client:visible — real inline bootstrap, waits for IntersectionObserver
(()=>{var a=(s,i,o)=>{let r=async()=>{await(await s())()},c={rootMargin:i?.rootMargin},n=new IntersectionObserver(e=>{for(let l of e)if(l.isIntersecting){n.disconnect(),r();break}},c);for(let e of o.children)n.observe(e)};(self.Astro||(self.Astro={})).visible=a;window.dispatchEvent(new Event("astro:visible"));})();
```

ดังนั้นมุมมองที่ตรงกว่าไม่ใช่ "`client:visible` ship JavaScript น้อยกว่า" — พิสูจน์ข้างบนแล้วว่า สำหรับ island เดียว มันส่ง byte *เท่ากันเป๊ะ*ในที่สุด สิ่งที่มันเปลี่ยนคือ critical path: bootstrap ของ `client:load` fire บน `astro:load` (แทบจะทันที) ในขณะที่ `client:visible` ตั้ง `IntersectionObserver` และ import chunk ของ component ก็ต่อเมื่อมัน scroll เข้ามาในจอจริง ๆ บนหน้าที่มีหลาย island ความต่างด้าน timing นี้แหละที่ทำให้ JS ของ carousel ที่อยู่ below-the-fold ไม่ไปแย่งอยู่ใน network waterfall *แรก* — byte ไม่ได้เล็กลง แค่ไม่ไปแย่ง bandwidth กับเวลา main-thread กับงาน above-the-fold ตอนโหลดครั้งแรกเท่านั้น

## Prefetch: config จริงและ script จริง

`prefetch` เป็น key config ระดับบนสุดจริง ตรวจสอบตรงจาก schema ที่ติดตั้งจริง (`astro/dist/core/config/schemas/base.js`):

```text
prefetch: boolean | { prefetchAll?: boolean, defaultStrategy?: 'tap' | 'hover' | 'viewport' | 'load' }
```

```js
// astro.config.mjs
import { defineConfig } from 'astro/config';

export default defineConfig({
  prefetch: { prefetchAll: true, defaultStrategy: 'viewport' },
});
```

เปิดใช้ แล้ว opt-in link ให้ตรง ๆ (หรือพึ่ง `prefetchAll`/defaultStrategy):

```astro
<a href="/pricing" data-astro-prefetch>Pricing</a>
```

attribute นั้นรอดไปถึง HTML ที่ build ออกมาโดยไม่ถูกแตะ — Astro ไม่ได้ rewrite มัน script prefetch แบบ global (`astro/dist/prefetch/prefetch.js` ที่ bundle ออกมาเป็น `prefetch.D-YIxd5A.js` ข้างบน) scan หา `data-astro-prefetch` เอง อ่านจาก script จริงที่ ship ออกมา: มันต่อ strategy จริงสามแบบ — `tap` (listener `mousedown`/`touchstart` ที่ fetch ด้วย `ignoreSlowConnection` ทันที), `hover` (listener `mouseenter`/`focusin` ที่ debounce 80ms ก่อน fetch ยกเลิกได้ด้วย `mouseleave`/`focusout`) และ `viewport` (`IntersectionObserver` คลุมทุก `<a>` ที่ match fire ทันทีที่ scroll เข้ามาในจอ) เมื่อคู่กับ `<ClientRouter />` prefetch ทำให้ navigation หลายหน้ารู้สึกเหมือน SPA — HTML ของหน้าถัดไปอยู่ใน cache ของ browser แล้วตอนที่คลิก — โดยไม่ต้องมี data layer ฝั่ง client เลย

## วัดสิ่งที่เรา ship จริง ๆ

อย่า optimize ด้วยความรู้สึก มีสองอย่างที่ต้องดู:

- **island ที่เรา ship จริง** build เว็บแล้วเช็คว่า component ไหนกลายเป็น island จริง (และด้วย directive อะไร) — พิสูจน์ข้างบนแล้วว่า `ls -l` จริงบน `dist/client/_astro/` คือความจริงพื้นฐาน ไม่ใช่การเดาจากการอ่าน source
- **Lighthouse / Core Web Vitals** รัน Lighthouse (ใน Chrome DevTools) กับเว็บที่ build แล้ว ดู Largest Contentful Paint (ปกติคือ hero image — ดู lesson เรื่อง asset), Cumulative Layout Shift (จองพื้นที่ image/font ไว้) และ Total Blocking Time (JavaScript ของ island)

baseline ของ Astro ปกติได้คะแนนเกือบเต็มออกจากกล่องอยู่แล้ว เมื่อคะแนนตก มักเป็นหนึ่งในสามอย่างนี้: image ที่ไม่ optimize, font ที่ทำให้เกิด shift หรือ island ที่ hydrate เร็วเกินความจำเป็น

## build เองก็เร็วขึ้น (Astro 7) — cite ไว้ ไม่ใช่จำมา

runtime performance คือสิ่งที่ผู้ใช้รู้สึก ส่วน build performance คือสิ่งที่*เรา*รู้สึกทุกครั้งที่ deploy อ้างจาก [Astro 7.0 release notes](https://astro.build/blog/astro-7/) ทางการตรง ๆ (ตรวจสอบด้วยการ fetch จริง ไม่ใช่จำมา): Astro 7 ย้ายไป **Vite 8** ที่ bundler ตอนนี้คือ **Rolldown** อธิบายไว้ว่า *"10-30x faster than Rollup in benchmarks while supporting the same Rollup and Vite plugin APIs."* rendering engine แบบ queued ใหม่ อธิบายไว้ว่า *"~2.4× faster"* กว่าวิธี recursive rendering แบบเดิม โดยรวม: *"overall build times improved by 15–61%, with some sites building more than twice as fast"* โดยเว็บที่ compile `.astro` และ process Markdown เป็นส่วนใหญ่ของ build จะได้ประโยชน์มากที่สุด

ผลข้างเคียงหนึ่งอย่างต่อ output: HTML ที่ ship ถูก compress ด้วยกฎ whitespace แบบ JSX โดย default (`compressHTML: 'jsx'`) ซึ่งเล็กลงนิดหน่อยแต่หมายความว่า newline ระหว่าง inline element ไม่ใช่ space อีกต่อไป — ดู lesson เรื่อง syntax

Astro ให้ baseline ที่เร็ว (static HTML, zero JS) งาน performance คือการรักษามันไว้ พิสูจน์ด้วย `ls -l` จริง: `client:load` กับ `client:visible` บน component เดียวกัน ship **byte เท่ากันเป๊ะ** — ต่างกันแค่*เวลา*ที่มันทำงาน (ทันที เทียบกับรอ `IntersectionObserver` fire) ดังนั้นเลือก `client:visible`/`client:idle` เพื่อให้การทำงานนั้นไม่อยู่บน critical path ไม่ใช่เพราะมัน ship น้อยกว่า `prefetch` เป็น config จริงที่ตรวจสอบจาก schema แล้ว (`prefetchAll`, `defaultStrategy`) ที่ script ของมันต่อ strategy `tap`/`hover`/`viewport` เข้ากับ link `data-astro-prefetch` และ**วัดผล** — เช็คว่า island ไหน ship จริง (ขนาดไฟล์จริง ไม่ใช่เดา) แล้วรัน Lighthouse — เพราะ regression มักเป็นหนึ่งใน: image ที่ไม่ optimize, font ที่ทำให้ shift หรือ `client:load` ที่ eager เกินไป ตัวเลขความเร็ว build เรื่อง Rolldown/queued-rendering ข้างบน quote มาตรง ๆ จาก release notes 7.0 ของ Astro เอง

## อ่านโค้ดที่ AI เขียน

- comment หรือ claim บอกว่า `client:visible` "ship JavaScript น้อยกว่า" `client:load` หรือเปล่า? พิสูจน์ข้างบนแล้วว่า: สำหรับ component เดียวกัน byte เท่ากันเป๊ะ — ต่างกันแค่ timing การทำงาน
- `client:load` ถูกใช้กับ component ที่ไม่มีเหตุผลจริง ๆ ต้อง hydrate ทันที (อยู่ below the fold ไม่ interactive ตอน first paint) หรือเปล่า? นั่นคือต้นทุนแบบ "hydrate ทุกอย่างล่วงหน้า" ที่ Astro มีไว้เพื่อเลี่ยงพอดี
- มี `<link rel="prefetch" href="...">` ที่เขียนเองใน `<head>` ของหน้า ทั้งที่ project เปิด config `prefetch` ของ Astro ไว้แล้วหรือเปล่า? นั่นคือการ reinvent สิ่งที่ `data-astro-prefetch` (หรือ `prefetchAll`) ทำให้อยู่แล้ว โดยไม่มี logic strategy hover/tap/viewport เลย
- ตัวเลขความเร็ว build (Rolldown, queued rendering) ถูก quote มาโดยไม่มีแหล่งที่มาหรือเปล่า? ตรวจสอบกับ release notes จริง — มันเป็น claim ที่ระบุตัวเลขและ version ชัดเจน ไม่ใช่ folklore
- claim เรื่องขนาด bundle ถูกพูดโดยไม่เคยรัน `ls -l` บน `dist/` จริงเลยหรือเปล่า? ขนาดจริงเปลี่ยนไปตาม version ของ Astro และ dependency ที่ update — cite จาก build ไม่ใช่จากความจำ

## Mental Model

client directive ไม่ได้เปลี่ยน*อะไร*ที่ island ต้องการ — component, glue ของ renderer และ framework runtime ที่แชร์กันเป็นชุดไฟล์เดียวกันไม่ว่าจะเลือก directive ไหน (พิสูจน์ข้างบนแล้วด้วย `ls -l` เหมือนกันเป๊ะสำหรับ `client:load` กับ `client:visible` บน component เดียวกัน) สิ่งที่ directive เปลี่ยนคือ*การจัดตาราง*เวลาล้วน ๆ: browser event จริงตัวไหน (`astro:load` ทันที, callback ของ `IntersectionObserver`, `requestIdleCallback`, media query) เป็นตัว trigger การ import งาน performance ตรงนี้คือการย้าย trigger นั้นให้ช้าลง ไม่ใช่การทำให้ JavaScript เล็กลง

## ข้อแลกเปลี่ยน

| | `client:load` | `client:idle` | `client:visible` | Prefetch (`data-astro-prefetch`) |
|---|---|---|---|---|
| **Byte ที่ ship สำหรับ component หนึ่งตัว** | เท่ากับ directive อื่น | เท่ากัน | เท่ากัน | N/A — prefetch HTML ไม่ใช่ JS |
| **ทำงานเมื่อไร** | ทันที (`astro:load`) | หลัง first paint ตอนว่าง | ทันทีที่ `IntersectionObserver` fire | ตอน tap/hover/viewport ตาม config |
| **แย่งกับ first paint ไหม** | แย่ง | น้อยกว่า | ไม่ จนกว่าจะ scroll ไปถึง | ไม่ |
| **เหมาะกับ** | interactivity above-the-fold ที่จำเป็นจริง ๆ (พบน้อย) | interactivity ที่ไม่เร่งด่วน | default สำหรับ island below-the-fold | ทำให้ navigation *ถัดไป* รู้สึกเร็วทันที |

## ความเข้าใจผิดที่พบบ่อย

- **"`client:visible` ship bundle เล็กกว่า `client:load`"** พิสูจน์ข้างบนแล้วด้วย `ls -l` จริงบน component เดียวกัน: byte เท่ากัน ต่างกันแค่ timing การทำงาน
- **"inline hydration bootstrap script คือส่วนที่หนักที่สุด"** มันแค่ glue ฝังในไฟล์ไม่กี่ร้อย byte ส่วนที่หนักจริงคือ chunk runtime ของ framework (ของ Preact ที่นี่คือ `preact.module`/`hooks.module`/`signals.module` รวมกัน ~20KB) — แชร์ครั้งเดียวต่อเว็บ ไม่ใช่ต่อ island
