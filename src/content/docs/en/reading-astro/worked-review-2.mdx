## The feature

The prompt was: *"Build a marketing site: a hero section, a newsletter signup form, a live chat widget, a testimonials section with a carousel and individual quote cards, and a promo banner shown three times on the page. Use view transitions between pages, and track page views with an analytics script."* The result below is the kind of first draft an AI assistant hands back — every island looks interactive, every import resolves, and the page genuinely renders. Read it the way the [reading order](/astro/en/reading-astro/) in this module's index recommends: islands and client directives first, then performance and caching, then security. It has **7 real bugs** — check the [AI bug catalog](/astro/en/reading-astro/ai-bug-catalog/) for the general pattern behind each one. This project uses only `@astrojs/preact` (the same integration this course's probe installs) — one of the seven bugs below is specifically about what happens the moment a *second* framework integration ever joins it.

## The review walk

### Islands & client directives: `<ViewTransitions />` — the name is gone

`MarketingLayout` imports `ViewTransitions` from `astro:transitions`, the pre-v5 name for the component.

<SpotTheBug code={`import { ViewTransitions } from 'astro:transitions';
---
<head>
  <ViewTransitions />
</head>`}>
Current Astro renamed this component to `ClientRouter` — and it isn't just deprecated or aliased, the old name is not exported at all. Proven in the probe with `astro check` against this exact import on Astro 7.3.5:

```text
error ts(2305): Module '"astro:transitions"' has no exported member 'ViewTransitions'.

import { ViewTransitions } from 'astro:transitions';
         ~~~~~~~~~~~~~~~
```

A real `astro build` fails the same way, one layer later, with a named bundler error:

```text
[ERROR] [vite] ✗ Build failed
[MISSING_EXPORT] "ViewTransitions" is not exported by "\0astro:transitions".
```

The fix is a straight rename — `import { ClientRouter } from 'astro:transitions'` and `<ClientRouter />` in the template — same import specifier, same behavior, just the current name.
</SpotTheBug>

### Performance & caching: an init script bound to `DOMContentLoaded`

The analytics script in the same layout sets itself up on `DOMContentLoaded` — the event that fires once, when the browser first parses the document.

<SpotTheBug code={`document.addEventListener('DOMContentLoaded', () => {
  console.log('ANALYTICS_INIT');
});`}>
Once `<ClientRouter />` (the fix above) is on the page, a link click no longer triggers a full page load — it's intercepted, the next page's HTML is fetched, and the DOM is swapped in place. `DOMContentLoaded` only ever fires on that first, real document load; it never fires again on a client-side swap, proven directly in the installed Astro source (`astro/dist/transitions/events.js`, `router.js`), which instead dispatches its own plain string event, **`astro:page-load`**, after *every* navigation — the first load and every subsequent client-side swap alike. This is the single most common view-transitions gotcha: the script "works" on the first page load and silently stops re-running the instant a visitor clicks anywhere. The fix is `document.addEventListener('astro:page-load', () => { ... })` — no import needed, it's a plain string event name (there is no exported `PAGE_LOAD`-style constant to import instead).
</SpotTheBug>

### Islands & client directives: a function prop into an island

`NewsletterForm` takes `onSubscribed: any` and the parent hands it a real function, `trackSubscribe`.

<SpotTheBug code={`export default function NewsletterForm({ placeholder, onSubscribed }: { placeholder: string; onSubscribed: any }) {
  // ...
}
---
<NewsletterForm placeholder="you@example.com" onSubscribed={trackSubscribe} client:visible />`}>
Island props travel from the `.astro` file to the browser as a JSON-ish string in the built HTML's `props` attribute — they must be serializable. Because `onSubscribed` is typed `any`, nothing at the type level stops a function from being passed, and the *runtime* behavior is silent data loss, not an error: Astro's own serializer falls through to `JSON.stringify` for anything it doesn't specifically recognize, and `JSON.stringify` of a function inside an array slot produces `null`. Proven with the real built `props` attribute for this exact call:

```text
props="{&quot;placeholder&quot;:[0,&quot;you@example.com&quot;],&quot;onSubscribed&quot;:[0,null]}"
```

`onSubscribed` is `null` on the client — the function simply never made the trip. If `NewsletterForm` calls `onSubscribed(email)` on submit, that throws `onSubscribed is not a function` at the moment someone actually submits the form — a confusing runtime error one interaction after the actual mistake. The fix is not passing a function as a prop at all: have the island call an Action or a plain `fetch()` itself (data the island already has, sent from inside the island), or pass only serializable data down and let the parent read the result back through an event/callback registered client-side, never as an island prop.
</SpotTheBug>

### Islands & client directives: `client:load` on a widget nobody sees on page load

`LiveChatWidget` sits at the very bottom of the page, below the testimonials, but hydrates with `client:load` — the most eager, most expensive directive, reserved for above-the-fold controls that must work the instant the page is usable.

<SpotTheBug code={`<LiveChatWidget client:load />`}>
`client:load` and `client:visible` compile into genuinely different loader scripts, verified directly in the real built output. `client:load`'s loader has **no gating condition at all** — it runs the hydrator the moment the custom element connects:

```text
(()=>{var e=async t=>{await(await t())()};(self.Astro||(self.Astro={})).load=e;window.dispatchEvent(new Event("astro:load"));})();
```

`client:visible`'s loader wraps the same call behind a real `IntersectionObserver`, and only fires once the element actually scrolls into the viewport:

```text
(()=>{var a=(s,i,o)=>{let r=async()=>{await(await s())()},t=typeof i.value=="object"?i.value:void 0,c={rootMargin:t==null?void 0:t.rootMargin},n=new IntersectionObserver(e=>{for(let l of e)if(l.isIntersecting){n.disconnect(),r();break}},c);for(let e of o.children)n.observe(e)};(self.Astro||(self.Astro={})).visible=a;window.dispatchEvent(new Event("astro:visible"));})();
```

A chat widget parked below the testimonials ships and executes its JavaScript for **every** visitor immediately on load, whether or not they ever scroll far enough to see it — exactly the eager-by-default reflex the AI bug catalog calls out. The fix is `client:visible`: the widget's JS never even loads for a visitor who leaves before scrolling to it.
</SpotTheBug>

### Islands & client directives: `client:only` with no framework hint

`TestimonialsCarousel` uses bare `client:only`, with no framework name.

<SpotTheBug code={`<TestimonialsCarousel quotes={["Great support!", "Worth every dollar"]} client:only />`}>
`client:only` skips server rendering entirely, so Astro has nothing to render-and-inspect to guess the framework from. With exactly **one** UI integration installed — this project's own `@astrojs/preact`, today — Astro quietly infers it, and this builds fine right now. The moment a **second** JSX-capable integration is ever added (a common step when a marketing site later pulls in a React-only embed widget), that inference becomes ambiguous, and the exact same line throws for real. Proven in a side probe with `@astrojs/preact` and `@astrojs/react` both installed, against this exact component name:

```text
[NoClientOnlyHint] Unable to render `TestimonialsCarousel`. When using the `client:only` hydration
strategy, Astro needs a hint to use the correct renderer.
  Hint:
    Did you mean to pass `client:only="react|preact|solid-js|vue (jsx)"`?
  Error reference:
    https://docs.astro.build/en/reference/errors/no-client-only-hint/
```

`astro check` and today's single-integration build both pass this file clean — the bug is latent, not currently failing, which is exactly why it's easy to ship. The fix costs nothing today and prevents the future break: `client:only="preact"`, naming the framework explicitly.
</SpotTheBug>

### Islands & client directives: `<slot />` inside a Preact component

`TestimonialCard` is a Preact component that writes `<slot />` in its JSX, the way an `.astro` component would.

<SpotTheBug code={`export default function TestimonialCard({ author }: { author: string }) {
  return (
    <blockquote class="testimonial">
      <slot />
      <footer>{author}</footer>
    </blockquote>
  );
}`}>
React, Preact, and Solid receive slotted children as a **`children`** prop — only Svelte and Vue use Astro's own `<slot />` element. `<slot />` inside a `.tsx` file compiles to a literal, native HTML `<slot>` element, which does nothing without a Shadow DOM around it — it is not a stand-in for `props.children`. Proven with a real build of this exact usage (`<TestimonialCard client:visible>` wrapping a server-rendered `<p>`):

```html
<blockquote class="testimonial"><slot></slot><footer>Sam, verified customer</footer></blockquote><template data-astro-template><p>This product changed how our team ships.</p></template><!--astro:end-->
```

The server-rendered quote never appears where it's supposed to — it's stranded inside a sibling `<template data-astro-template>` tag (Astro's own mechanism for carrying slotted content to the client for hydration), while the component itself rendered an empty, inert `<slot></slot>` in its place. The fix is `{props.children}` in place of `<slot />` — the same content, read the way Preact actually exposes it.
</SpotTheBug>

### Performance & caching: `is:inline` on a script meant to run once per page

`PromoBanner` is placed three times on the homepage, and its countdown-init script is marked `is:inline`.

<SpotTheBug code={`<div class="promo">Sale ends soon — free shipping over $50</div>
<script is:inline>
  console.log('PROMO_COUNTDOWN_INIT');
</script>`}>
A plain (non-`is:inline`) `<script>` in a component used multiple times on one page is bundled and **deduplicated** — Astro emits it exactly once, no matter how many instances of the component appear. `is:inline` opts out of both: the tag is emitted **exactly as written, once per instance**, with no bundling and no dedup. Proven with a real build of this exact component used three times on one page:

```text
PROMO_COUNTDOWN_INIT
PROMO_COUNTDOWN_INIT
PROMO_COUNTDOWN_INIT
```

Three identical `console.log` lines — the countdown-init logic runs three separate times, once per banner, instead of once for the page. Removing `is:inline` and building the identical three-banner page again produces exactly one:

```text
PROMO_COUNTDOWN_INIT
```

The fix is deleting `is:inline` here — this script has no reason to run unprocessed or per-instance. `is:inline` is for a script that genuinely must ship raw and repeated (an inline analytics snippet a vendor requires verbatim), not a reflex applied to every script tag.
</SpotTheBug>

## Mental Model

Every one of these seven bugs ships something to the browser that isn't what the AI-generated code assumed — a component name that no longer exists, an event that only fires once, a prop that silently becomes `null`, a script that runs eagerly or repeatedly against the author's intent, a `<slot />` that renders as an inert native tag. None of them are wrong *logic* — the code does exactly what it says. What's wrong is the assumption about what Astro's compiler or runtime actually does with that exact syntax, and the only way to catch that is to read the real, built output: a `props` attribute, a loader script, a duplicated `console.log`, an empty custom element.

## Common Misconceptions

- **"If a client directive is present, the component is behaving correctly."** `client:load`, bare `client:only`, and `is:inline` are all present, syntactically valid, and produce a working page today — the bug in each case is *which* directive, not whether one exists at all.
- **"A prop passed into an island is just a normal JavaScript value once it's on the client."** Proven above: a function prop silently becomes `null` — nothing you can call, and no error until the callback actually fires.
- **"Since React/Preact and Astro both use `<slot />`-like concepts, they work the same way inside a framework component."** Proven above: Astro's own `.astro` files use `<slot />`; React, Preact, and Solid use a `children` prop instead — writing `<slot />` inside a `.tsx` file compiles to an inert native HTML element, not a content projection point.
