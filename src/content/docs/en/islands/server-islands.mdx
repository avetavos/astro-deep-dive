## The problem server islands solve

Client islands are about *client-side* interactivity. **Server islands** solve a different problem: a page that is mostly cacheable and static, but has one part that is **personalized or slow** — the logged-in user's avatar, a "recommended for you" strip, a live price that needs a fresh query.

Without server islands you're forced to choose: render the whole page on demand (losing the cache on the 95% that never changes), or give up the personalized part. Server islands let you have both — **cache the shell, defer the dynamic bit.**

## `server:defer`

Add the **`server:defer`** directive to any `.astro` component to turn it into a **server island**. Astro then renders the rest of the page immediately — without waiting for that component — and the deferred component's real HTML is fetched separately and swapped in when ready.

```astro
---
import Avatar from '../components/Avatar.astro';
---
<Avatar server:defer />
```

The page's initial HTML ships right away and can be cached at the edge. The `Avatar` renders **on the server** — so it can safely read cookies, a session, or a database — but *out of band*, on its own request, after the shell is already on screen.

## Fallback content with `slot="fallback"`

Because the real content arrives a moment later, you provide **fallback** content to show in the meantime — a skeleton, a spinner, or a generic placeholder — using `slot="fallback"`:

```astro
---
import Avatar from '../components/Avatar.astro';
import GenericAvatar from '../components/GenericAvatar.astro';
---
<Avatar server:defer>
  <GenericAvatar slot="fallback" />
</Avatar>
```

The `GenericAvatar` renders into the cached shell immediately; the personalized `Avatar` replaces it once its own server render returns.

## The real built HTML

The fallback content, the fetch, and the swap are not hidden framework magic — building a real page with a `server:defer` `Avatar` (fallback `GenericAvatar`) and reading the actual output shows all three, in order, in plain HTML:

```astro
---
// src/components/GenericAvatar.astro
---
<img src="/generic-avatar.png" alt="Generic avatar" width="48" height="48" />
```

```astro
---
// src/components/Avatar.astro
const cookie = Astro.request.headers.get('cookie');
const userId = cookie?.match(/uid=(\\w+)/)?.[1] ?? null;
---
<div data-testid="avatar-real">
  {userId ? <p>Welcome back, user {userId}</p> : <p>Anonymous (no uid cookie forwarded)</p>}
</div>
```

```astro
---
// src/pages/server-island-demo.astro
import Avatar from '../components/Avatar.astro';
import GenericAvatar from '../components/GenericAvatar.astro';
---
<html><body>
<h1>Server island demo</h1>
<Avatar server:defer>
  <GenericAvatar slot="fallback" />
</Avatar>
</body></html>
```

```html
<!DOCTYPE html><html><link rel="preload" as="fetch" href="/_server-islands/Avatar?e=FDA01BAC8D95CB8E26A560DAB87l7Jmcc5evsrWx2DYJJRT%2BfX1KJFY%3D&amp;p=&amp;s=" crossorigin="anonymous"><body><h1>Server island demo</h1><script>async function replaceServerIsland(id, r) { let s = document.querySelector(`script[data-island-id="${id}"]`); if (!s || r.status !== 200 || r.headers.get('content-type')?.split(';')[0].trim() !== 'text/html') return; let html = await r.text(); while (s.previousSibling && s.previousSibling.nodeType !== 8 && s.previousSibling.data !== '[if astro]>server-island-start<![endif]') s.previousSibling.remove(); s.previousSibling?.remove(); s.before(document.createRange().createContextualFragment(html)); s.remove(); }</script><!--[if astro]>server-island-start<![endif]--><img src="/generic-avatar.png" alt="Generic avatar" width="48" height="48"><script type="module" data-astro-rerun data-island-id="f07047c9-f26d-45fe-a9ea-1ac642bcc610">const headers = new Headers({});

```

Four real pieces, in the exact order they appear:

1. A `<link rel="preload" as="fetch">` in `<head>` — the browser starts fetching the server island's endpoint before it even reaches the body, without blocking render.
2. The shared `replaceServerIsland` runtime script — the same ~15 lines regardless of how many server islands the page has.
3. The `GenericAvatar` fallback markup, right where `Avatar` will end up — this is what paints first.
4. A `<script type="module" data-island-id="...">` that repeats the same URL from the preload `fetch`, then calls `replaceServerIsland(id, response)` to swap the fallback for the real HTML once it arrives.

## Props encryption

Props (and slot content) passed to a server island are not sent to the browser in plain text — the URL above (`?e=...&p=&s=...`) is genuinely encrypted, not just obfuscated. Astro's own source (`astro/dist/core/encryption.js`) uses **AES-GCM** with a 256-bit key generated fresh per build and stored server-side; per the official docs (`docs.astro.build/en/guides/server-islands/#reusing-the-encryption-key`):

> Astro uses cryptography to encrypt props passed to server islands, protecting sensitive data from accidental exposure. This encryption relies on a new, random key that is generated on each build and embedded in the server bundle.

A fresh key every build means a CDN caching a page across deploys, or a rolling deployment where old and new server instances briefly coexist, can end up with a decryption mismatch. The fix is `astro create-key`, which generates a stable key to set as the `ASTRO_KEY` environment variable so every build (and every backend instance) encrypts and decrypts with the same key.

## Cache headers on the response — proven, and not what you might assume

A real `curl -D -` against the built `_server-islands` endpoint (headers only, from a real running build):

```text
$ curl -s -D - "http://127.0.0.1:4601/_server-islands/Avatar?e=...&p=&s=" -o /dev/null
HTTP/1.1 200 OK
content-type: text/html
x-robots-tag: noindex
Date: Sat, 26 Sep 2026 02:35:38 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked
```

There is **no `Cache-Control` header at all** by default — only `x-robots-tag: noindex` (so search engines don't index the raw fragment endpoint). Astro does not cache a server island's response for you; if the fragment is cacheable, you set `Cache-Control` yourself inside the component (e.g. `Astro.response.headers.set('Cache-Control', ...)`), the same way you would for any other on-demand route.

## Server islands need an adapter, even on an otherwise fully static site

The requirement isn't soft advice — leave the adapter out of an otherwise `output: 'static'` project that uses `server:defer` anywhere, and the build fails immediately, before it even gets to prerendering pages:

```text
[NoAdapterInstalledServerIslands] Cannot use server islands without an adapter. Please install
and configure the appropriate server adapter for your final deployment.
  Hint:
    See https://docs.astro.build/en/guides/on-demand-rendering/ for more information.
  Error reference:
    https://docs.astro.build/en/reference/errors/no-adapter-installed-server-islands/
```

(Reproduced against a real `astro build` with `output: 'static'` and no `adapter` set at all, one page using `server:defer`.) Adding `adapter: node({ mode: 'standalone' })` — or any adapter — back makes the exact same project build clean; nothing else about the page needs to change.

## Cookies inside a server island

A server island's fetch runs same-origin from the browser, and a same-origin `fetch()` sends cookies by default (no `credentials` option needed) — so `Astro.request.headers.get('cookie')` inside `Avatar.astro` really does see the visitor's cookies, proven with a real browser session: set `document.cookie = 'uid=99'`, navigate fresh to the page, and once the deferred fetch resolves:

```text
document.querySelector('[data-testid=avatar-real]').outerHTML
// "<div data-testid=\"avatar-real\"><p>Welcome back, user 99</p></div>"
```

— versus the fallback-then-generic-anonymous response you get with no cookie set at all (`"Anonymous (no uid cookie forwarded)"`, proven earlier via a direct `curl` with no `Cookie` header). Nothing special has to be done to forward the cookie; it's an ordinary same-origin request from the browser's point of view.

## When to use them (and the adapter requirement)

Server islands are the right tool when a page is **cacheable except for a small dynamic piece**:

- A marketing or product page that's identical for everyone *except* a personalized greeting or cart.
- A mostly-static page with one **slow** query you don't want blocking first paint.
- Auth-gated fragments on an otherwise public, CDN-cached page.

Two things to remember. First, `server:defer` renders **on the server**, so it needs an **adapter** installed (Cloudflare, Node, Vercel...) — the same requirement as any on-demand rendering; without one you'll hit the real `NoAdapterInstalledServerIslands` build error proven above, even on an otherwise fully static, adapter-free project. Second, it's not for client interactivity — if the piece needs to respond to clicks, that's a *client* island (a client directive), possibly in addition. Server islands are about deferring **server-rendered** output, not hydrating JavaScript.

## Reading AI-generated code

When a generated snippet uses `server:defer`, check for these before trusting it:

- Is `server:defer` used on a page/project with no adapter configured? It's a real, immediate build failure (`NoAdapterInstalledServerIslands`, proven above) — not a warning, not something that only shows up at runtime.
- Does the component assume props are sent in plain text over the wire because "it's just a query string"? Proven above: the `e`/`p`/`s` params are AES-GCM encrypted, not just present — but also not free of operational cost (a fresh key per build, unless `ASTRO_KEY` is set).
- Does a comment or assumption claim the server-island response is "automatically cached" or "cached at the edge like the shell"? Proven above with a real `curl -D -`: no `Cache-Control` header ships by default — only the shell around it is cacheable unless the component sets its own header.
- Is `server:defer` reached for on a component that needs to respond to a *click*? That's client interactivity — a client directive, not a server island; the two solve different problems and can be combined but aren't substitutes.
- Does the fallback (`slot="fallback"`) render something that quietly assumes cookies/auth state (defeating the point of a fast, cacheable shell)? The fallback is what every visitor sees first, cache included — it should be generic by design, with the personalized part arriving only in the deferred fetch.

## Mental Model

A server island is the mirror image of a client island: a client island ships JavaScript to defer *when a component becomes interactive*; a server island defers *when a component's server render happens* — after the shell has already shipped, on its own request, so the slow or personal part never blocks the fast, cacheable part. Both are "defer this piece, ship everything else now" — one on the client's timeline, one on the server's.

## Trade-offs

| | Prerendered page | On-demand page | Server island (`server:defer`) |
|---|---|---|---|
| **Cacheable?** | Fully | Not by default | The shell yes, the island only if you set `Cache-Control` yourself (proven above) |
| **Sees cookies/session?** | No (built once, ahead of any request) | Yes | Yes — proven above, a real cookie reached `Astro.request.headers` |
| **Needs an adapter?** | No | Yes | Yes — proven above, even if the rest of the site is fully static |
| **Blocks first paint on the slow bit?** | N/A (nothing dynamic) | Yes, the whole page waits | No — the shell ships first, the island arrives after, swapped over a fallback |

## Common Misconceptions

- **"The server island's own response is cached along with the shell."** Proven above with a real `curl -D -`: no `Cache-Control` header ships by default. Caching the fragment is something you opt into yourself, inside the component.
- **"Props sent to a server island are visible in the page source, like a normal query string."** Proven above and confirmed in Astro's own source: they're AES-GCM encrypted, not plain text — though the key is fresh per build unless `ASTRO_KEY` is set, which matters for CDNs and rolling deploys.
- **"A fully static site never needs an adapter."** True until the first `server:defer` — proven above, the build fails immediately (`NoAdapterInstalledServerIslands`) the moment one appears anywhere in the project, however static everything else is.
- **"A server island can't see the visitor's cookies because the fetch is a separate, out-of-band request."** Proven above with a real browser session: the fetch is same-origin, so the browser sends cookies with it by default — `Astro.request.headers.get('cookie')` sees exactly what a normal page load would.

<Callout title="The one-line takeaway">
`server:defer` turns an `.astro` component into a **server island**: the page's shell renders and ships immediately (so it stays cacheable), while the deferred component renders **on the server on its own request** — over a real `<link rel="preload">` + fetch + swap, proven in the built HTML above — and its HTML is swapped in over a `slot="fallback"` placeholder when ready. Props are AES-GCM encrypted (a fresh key per build unless `ASTRO_KEY` is set), the response itself is **not cached** unless you set `Cache-Control` yourself, and cookies **do** reach the component (same-origin fetch). It renders on the server, so it **requires an adapter** — a real, immediate build error without one, even on an otherwise fully static project — and it's about deferring server output, not client interactivity.
</Callout>
